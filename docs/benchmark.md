# 브로드캐스트 전략 벤치마크

## 목적
매 tick 플레이어 위치를 전원에게 보내는 비용이 접속자 수에 따라 어떻게 늘어나는지, AOI와 격자 버킷이 그 비용을 어디까지 줄이는지 측정한다. 분포(흩어짐/몰림)에 따라 결론이 달라지는지도 본다.

## 방법
- **서버** `bench/game_server_bench.cpp`: 본 서버와 같은 epoll ET + timerfd 50ms tick. 전송 전략을 모드 스위치로 바꾼다. 비교를 공정하게 하려고 델타 스냅샷은 끄고(매 tick 전체 위치를 보냄), 충돌 검사는 O(1)로 고정했다.
- **봇** `bench/bot.cpp`: 헤드리스 클라이언트 N개가 접속해 매 tick 무작위 이동 패킷을 보내고 스냅샷을 받는다.
- **모드**
  - A 전체 브로드캐스트: 스냅샷 하나를 만들어 전원에게 같은 내용을 보낸다.
  - B AOI 선형: 수신자마다 전체 플레이어를 훑어 체비쇼프 거리 20 이내만 담는다.
  - C AOI 격자: 월드를 20×20 버킷으로 나눠 매 tick 재구성하고, 수신자의 버킷과 이웃 8개(3×3)만 조회한 뒤 정밀 거리로 거른다.
- **분포**
  - 균일: 봇을 월드 전체에 고르게 배치. 접속자 수에 맞춰 월드 한 변을 44→76→99→140→199로 키워 밀도를 약 0.05명/칸으로 고정한다. "세계가 커지는" 시나리오.
  - 밀집: 월드를 59×59로 고정하고 봇을 몰아넣는다. 2000명이면 0.57명/칸이고, 관심 반경(41×41칸)이 월드의 절반을 덮어 사실상 모두가 서로를 본다.
- **접속자 수**: 100, 300, 500, 1000, 2000. 2분포 × 5수 × 3모드 = 30회.
- **측정**: 접속 완료 후 120 tick(6초) 동안 tick마다 스냅샷 생성 시간(build), 전송 시간(send), tick 총 처리 시간, 보내려 한 바이트와 실제 write된 바이트를 기록한다. `bench/run_bench.sh`가 30회를 돌리고 `bench/aggregate.py`가 `results/summary.csv`와 `report.html`로 모은다.
- **환경**: WSL2 Ubuntu, g++ -O2, 서버와 봇이 같은 머신에서 localhost로 통신. CPU Intel Core i7-12700F(12코어 20스레드, WSL2에 할당된 논리 프로세서 20개).

## 해석
1. **전체 브로드캐스트는 정확히 N²이다.** 2000명이면 tick당 48MB, 초당 960MB를 만들어야 하고, 50ms 예산을 넘겨 tick이 15.6/s로 무너진다. 실제 네트워크에서는 애초에 불가능한 대역폭이다.
2. **AOI는 전송량을 N에 가깝게 만든다.** 균일 분포 2000명에서 한 사람이 받는 스냅샷이 평균 79명분이다. 밀도 0.05명/칸 × 반경 41×41칸 ≈ 84명과 맞고, 그래서 전송량이 1/25로 준다.
3. **격자의 이득은 전송량이 아니라 탐색 비용이다.** B와 C는 같은 집합을 보내므로 전송량이 같고(차이는 런 편차 ±8%), 후보를 찾는 비용만 다르다. 2000명에서 스냅샷 생성이 B 16.3ms, C 6.6ms로 2.5배 차이고, tick 총 시간은 34.6ms 대 24.4ms다. 접속자가 더 늘면 B는 build 시간이 N^1.5로 늘어 먼저 예산을 넘긴다.
4. **밀집 분포에서는 AOI가 무력하다.** 모두가 서로의 반경 안이면 보내야 할 정보 자체가 N²이라 C도 지수 1.98로 늘고, 2000명에서 A의 1/3에 그치며 세 방식 모두 예산을 넘긴다. 구현의 한계가 아니라 문제의 하한이다. 몰림에는 관심 대상 수 상한, 먼 대상의 갱신 빈도 낮추기, 인스턴스 분리 같은 다른 수단이 필요하다.
5. **남은 병목은 write다.** B·C의 전송 시간이 2000명에서 17~18ms로 같고, 바이트보다 클라이언트별 write 호출 N번이 지배적이다. 다음 순서는 델타 스냅샷(본 서버에는 구현돼 있고 이 벤치에서는 껐다)과 write 묶기다.

## 한계
- localhost 단일 머신이라 실제 네트워크 대역폭·지연은 측정하지 않았다. 보내려 한 바이트와 write된 바이트가 항상 같아 백프레셔도 없었다. 측정한 것은 서버의 연산량과 생성 바이트의 스케일링이다.
- 봇과 서버가 CPU를 나눠 쓴다. 절대값보다 모드 간 비교와 증가 지수가 의미 있다.
- 각 조합을 1회 측정했다. B와 C의 전송량 차이(±8%)는 봇의 무작위 이동에 따른 런 편차다.
- 델타 OFF 상태의 수치다. 델타를 켜면 idle 플레이어가 많을수록 전송량이 더 준다.

## 재현
```bash
cd bench
g++ -std=c++17 -O2 -o game_server_bench game_server_bench.cpp
g++ -std=c++17 -O2 -o bot bot.cpp
./run_bench.sh          # 인자 없음. 2분포 × 5수 × 3모드 = 30회, 각 3초 워밍업 + 6초(120 tick) 측정
python3 aggregate.py    # results/summary.csv, report.html
```
